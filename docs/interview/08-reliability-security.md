# 08. 安全、可靠性、性能、测试与运维

本章将已有机制和上线扩展分开。它是面试设计材料，不是本次对系统做完整安全审计或生产容量认证的结果。

## 1. 必须维护的系统不变量

1. 用户只能访问授权工作区、项目和数据范围。
2. 模型或文档文本不能改变租户、凭据、工具权限和预算。
3. 已发布结论可以追溯当时的证据与版本。
4. 同一个终态不能被迟到回调无条件反向覆盖。
5. 接受任务、完成任务、呈现结果是可区分的状态。
6. 失败后能解释已发生哪些副作用、哪些可以重试。
7. 文件、数据库行、向量和缓存的生命周期能够对账。

## 2. 一致性：不止一句「最终一致」

### 2.1 上传与索引故障窗口

| 步骤 | 失败窗口 | 可观察状态 | 处理思路 |
| --- | --- | --- | --- |
| 存对象 | 上传中断、SDK 超时 | 没有完整资产或失败提示 | 中止上传/清理分片，避免重复占配额 |
| 写资产 | 对象已写、DB 回滚 | 孤儿对象 | 当前局部补偿 + 后台对账方案 |
| 派发索引 | DB 提交、进程崩溃 | INDEXING 停滞 | Outbox 或可恢复调度扫描方案 |
| 生成向量 | Provider 超时或维度错误 | 索引失败 | 有界重试、明确配置错误、保留原文件 |
| 替换 PG Chunk | 删旧写新部分失败 | 事务回滚 | 检查事务边界与旧向量状态 |
| 写 Milvus | PG 已提交而向量写失败 | PG/Milvus 不一致 | 标记失败、重建，后续版本化切换 |
| 成功回写 | AI 成功但回调失败 | Java 仍显示进行中 | 快照协调、回调重试与幂等 |
| 缓存失效 | 新数据已写、版本未更新 | 旧检索结果 | 确认失效完成/版本协调，TTL 最终兜底 |

### 2.2 Outbox、Saga、对账分别解决什么

- Outbox：业务记录与待发送事件在同一数据库事务提交，派发器可靠重试；解决提交与消息发送之间的丢失窗口。
- Saga/补偿：多个非原子步骤失败后执行语义补偿；删除文件并不是撤销外部模型已经产生的账单。
- 对账：定期比较数据库引用、对象和索引，修复长期漂移；它是兜底，不替代实时错误处理。
- 幂等：重复处理不会产生不期望的新业务结果；不仅是 HTTP 方法名，也需要业务键和持久化约束。

以上是可采用的架构手段。当前局部实现不等于完整部署分布式事务框架。

## 3. 状态机与幂等

### 3.1 运行状态

QUEUED → RUNNING → COMPLETED/FAILED；取消可能先 CANCELLING 再 CANCELLED。界面关闭、SSE 断开、模型超时和用户主动取消是不同事件。

幂等键应按用途区分：创建消息的 client_message_id、运行的 run_key、导入行动的来源键、外部写工具的 operation_id。一个 ID 不能在所有场景重复复用而掩盖实际重试。

### 3.2 顺序和版本

回调可以重复或乱序，消息系统只有局部顺序时要以版本/序号/预期状态控制写入。扩展方案是：UPDATE run SET ... WHERE id=? AND version=? AND status IN (...)，影响 0 行则重新读取并协调。

对报告签署，核对 snapshot_hash 与 report_version；对计划修改，核对 plan_version；对索引发布，核对 asset/index version。这些都是同一个思想：决策必须绑定当时读取的内容。

## 4. 恢复目标与服务降级

| 故障 | 允许的降级方向 | 必须避免 |
| --- | --- | --- |
| 外部模型不可用 | 保留历史报告、检索/资料浏览，明确新任务失败 | 展示 mock 答案冒充真实分析 |
| 外部搜索不可用 | 只使用已有内部证据，注明范围 | 悄悄编造「最新资料」 |
| 向量能力不可用 | 若当前路径支持，退关键词并标有效模式 | 把索引失败当无相关资料而下结论 |
| OCR 不可用 | 保留文件、警告文本缺失 | 空文本仍显示完整理解成功 |
| Redis 不可用 | 根据职责决定缓存重算/拒绝新任务/受控回退 | 所有关键状态一律当缓存可丢 |
| SSE 不可用 | 快照轮询和最终内容恢复 | 重新创建一份相同付费任务 |

降级必须可见且不扩大授权。单独的 /health 不能覆盖这些业务语义。

## 5. 多实例扩展前的状态清单

当前状态分布：Java HttpSession/SessionRegistry、SSE subscribers/进程锁；Python _active_runs、EventBus、角色消息队列、工具 semaphore、热快照、本地缓存锁。

直接把 backend/ai-service 副本数改成 3，会产生会话漂移、事件推错实例、取消不生效、重复执行和预算变成三倍等问题。

较完整的扩展顺序：

1. 共享会话或重新设计认证，并验证退出和踢设备。
2. 用持久化 Run 状态和原子认领控制执行所有权。
3. 共享事件日志/总线，明确回放与订阅路由。
4. 将取消、暂停和计划版本变更广播到执行节点。
5. 将并发/成本预算从进程内扩大到租户/全局范围。
6. 总量计算数据库连接、模型 QPS、内存和队列速率。
7. 注入故障验证扩容后语义保持一致。

Kubernetes 可以管理 Pod 与探针，但不能替应用完成上述状态设计。

## 6. 安全面试按入口分析

### 6.1 账号与会话

已有 BCrypt、验证码、Redis 原子限流、CSRF、Cookie 属性、会话上限和生产启动校验。要进一步验证账号枚举、密码重置绑定、验证码目的隔离、并发一次性消费和新旧会话处理。

生产必须启用 HTTPS、Secure Cookie 和明确 Origin；当前 Nginx 未配置 TLS。不要把 HTTP 开发默认值直接称为生产安全部署。

### 6.2 租户与对象级授权

覆盖工作区、项目、Run、Thread、Message、资产、Chunk、附件、报告、审查和行动项。攻击者可能只替换 URL 中的一个 ID；后端必须验证整个关联链。

验证矩阵至少有：同工作区不同项目、不同工作区、被移除成员、只读角色、猜测他人附件 ID、旧邀请、私有配置、运行归属不一致。只测「未登录返回 401」不能证明对象级授权正确。

### 6.3 SQL、Cypher 和表达式注入

SQL 使用参数绑定，排序/动态字段用白名单；Cypher 使用参数；Milvus 过滤 ID 经数值转换。不能把模型生成的 SQL、Cypher、表达式或路径直接执行。

参数化不自动限制查询成本，合法输入仍可能导致大范围扫描、正则高耗或无界遍历，因此还需长度、数量、深度和超时限制。

### 6.4 上传与转换

文件扩展名、Content-Type、内容特征都只是不同信号，不能仅信任浏览器 MIME。还需防路径穿越、超大解压、恶意格式、资源耗尽、转换器漏洞和敏感文件外传。

当前有类型/大小/配额与解析上限，镜像以普通用户运行。更强隔离可以把转换作业放到低权限、无额外网络、限 CPU/内存/时长的独立执行环境，这是后续方案。

### 6.5 SSRF：URL 校验的明确边界

security/policy.py 允许无凭据 HTTP(S)，拒绝 localhost、部分内部域名和私有/保留 IP 字面量；函数注释明确「不做 DNS 解析」，要求网络客户端继续实施 egress allow-list 和解析地址检查。

因此不能声称完全阻断 DNS rebinding、域名解析到内网或重定向绕过。当前部分抓取允许 follow_redirects，强化时要检查每次重定向和最终连接地址，并配合网络层阻止元数据/内网访问。这里是代码边界说明，不是已完成漏洞验证结论。

### 6.6 Prompt Injection 与工具授权

将文档、网页和远程工具文本当数据；工具只能来自注册表，租户由可信上下文注入，预算和确认由代码执行。模型说「我已经得到用户授权」不能替代系统保存的授权状态。

防御不是关键词过滤几个「忽略指令」短语，而是减少模型可控制的权限参数、保持来源分层、限制可执行能力、验证输出和审计副作用。

### 6.7 秘密与日志

模型凭据使用 AES-GCM，解密只在运行需要时进行；日志、事件 payload、错误和接口响应应脱敏。加密主密钥与数据库备份一起丢失/泄露，会影响可恢复性或保密性。

root .env 不应提交；环境变量仍可被有容器管理权限的人查看。秘密轮换需要新旧版本兼容或重加密流程，不是随意换一个字符串。

### 6.8 代理信任和限流 IP

Nginx 传转发 Header，AuthRateLimiter 使用 getRemoteAddr。要实际核对 Servlet 的可信代理还原设置：否则所有用户可能共用代理 IP 的限流桶；无条件信任客户端传来的 X-Forwarded-For 则可能绕过限流。

## 7. 性能：先建立分段模型

总延迟近似为：请求/排队 + 上下文准备 + 解析 + 检索 + 模型多次调用 + 工具 + 审查 + 持久化/传输。流式首字快不代表总任务快；缓存命中时快不代表冷启动和尾延迟合格。

| 层 | 观察指标 | 常见瓶颈 |
| --- | --- | --- |
| 浏览器 | 首屏、长任务、内存、输入延迟 | 大包、Markdown/高亮重算、长列表 |
| Nginx | 连接数、上游响应、5xx | 超时、缓冲、上传临时空间 |
| Java | CPU、GC、池等待、请求分位 | 长事务、全量查询、事件集合增长 |
| PostgreSQL | 慢 SQL、锁、连接、buffer/IO | 缺索引、统计偏差、JSON/TEXT 过量 |
| Python | event loop lag、任务数、线程池 | 同步 SDK、解析 CPU、无界任务 |
| Redis | used memory、eviction、latency、Pending | 大 key、持久化、队列积压 |
| Milvus | load/index/search 时延、内存 | 候选过多、集合规模、索引/磁盘 |
| 模型 | 首响应、总耗时、429、Token | 上下文过长、反复审查、Provider 限额 |

## 8. 容量估算与排队

Little's Law 可用于稳定系统的平均量估算：在途任务数 L≈到达率 λ×平均处理时间 W。假设每秒 1 个任务、平均 40 秒，约 40 个在途任务；这是情景算式，不是当前实测吞吐。

若只有 8 个 Worker 且每个任务平均占用 40 秒，粗略服务能力约 0.2 个/秒，持续每秒 1 个到达会积压。实际存在 I/O 重叠、多步骤和限流，应测队列等待与模型并发占用，而不是只看协程数量。

容量还需：

- 文件容量 = 原文件 + 解析/生成物 + 备份/版本保留。
- 向量容量 ≈ Chunk 数×维度×4 字节，再加索引和元数据。
- 数据库连接 = Σ各副本池上限 + 运维/迁移余量。
- Token 成本 = Σ每次调用的输入/输出×对应单价，含重试、审查、Embedding 和搜索。
- SSE 连接消耗 FD、内存及应用对象；断线订阅者需要释放。

## 9. 限流、隔离、超时、重试与熔断

这些机制不能混成一个重试装饰器：

- 限流限制进入速度，按用户/工作区/Provider 分层。
- 并发隔离限制同时占用资源，避免 OCR 抢光聊天能力。
- timeout 限制等待阶段，需区分 connect、first response、idle、total。
- retry 处理可恢复错误，使用上限、退避和抖动，并避免非幂等副作用。
- circuit breaker 在持续失败时短时拒绝，减少雪崩；当前不应声称已有完整熔断组件。
- backpressure 将过载显式反馈到接收层，避免无界排队。

## 10. 测试体系按风险分层

### 10.1 单元测试

覆盖切片、融合、重排、权限策略、状态迁移、来源键、数字/引用规则、错误映射。mock 测试确定逻辑契约，不证明真实 PostgreSQL/Milvus/Provider 的行为。

### 10.2 集成与契约

用真实数据库验证迁移、唯一约束、JSONB、全文 SQL、行锁与权限 JOIN；真实 Milvus 验证维度、租户过滤、删除和可见性；跨 Java/Python 验证字段命名、ID 精度、错误码、回调和 SSE payload。

### 10.3 E2E

注册/登录 → 工作区 → 项目 → 上传 → 索引 → 检索 → 创建 Run → SSE → 报告 → 审查 → 行动项 → 提交证据 → 验收。至少分别使用 mock 和真实 Provider，记录配置及区别。

### 10.4 故障注入

| 故障动作 | 验证目标 |
| --- | --- |
| Worker 处理后、ACK 前退出 | 重投递不造成错误重复结果 |
| 模型调用超过 Pending 回收阈值 | 心跳避免活跃任务被误回收 |
| Redis 短断与重连 | 降级可见、恢复不重复派发 |
| 回调重复/乱序 | 终态与 Token 统计幂等 |
| 索引到一半 Milvus 失败 | 状态明确、可重建、无越权残留 |
| 修改报告后签旧审查 | 版本检查拒绝旧决定 |
| 删除资产同时重建 | 已删除内容不会被迟到写回 |
| 浏览器刷新/断线 | 不重建付费 Run，恢复快照 |
| 两份并发大文件 | 配额不超限且失败可补偿 |

### 10.5 现有证据怎样报告

2026-10-18 验收记录：前端 49 通过；Python 339 通过、7 跳过；Java 61 通过、2 跳过。必须同时说跳过原因和 mock 模型限制，不能把通过数量当覆盖率，也不能把记录当本次重新执行结果。

## 11. 日志、指标、Trace 与审计

日志解释单次错误，指标看长期趋势与告警，Trace 串联跨服务调用，审计记录谁何时改了关键业务事实。四者各有用途。

建议关联 requestId/traceId/runId/workspaceId/projectId/userId、stage/tool/provider，但对外展示应减少个人信息。一个 Run 多次 Provider 调用需要 callId 才能归因重试与费用。

可定义业务目标，例如「被接受任务的最终可解释终态比例」「P95 排队时间」「引用可验证比例」，而非只告警 CPU 80%。阈值要基于实际负载，不在面试中编造已经达成的 SLO。

## 12. 上线、发布与恢复

### 发布前

固定镜像版本/digest，校验配置和默认秘密，验证迁移向前/回滚兼容，完成必要测试；准备数据库、对象和密钥备份；确认真实模型与出站网络；明确本次上线验收指标。

### 发布时

先处理依赖兼容，再让新实例通过 readiness 与业务冒烟，逐步引流；后台 Worker 排空和队列认领要避免重复；SSE 长连接需要可恢复终止。

### 回滚时

镜像可回滚不代表数据库可回滚。若新版本删除旧列或改变加密/消息格式，旧镜像可能无法运行；应在变更前设计兼容期。对已生成的外部副作用，用业务补偿而不是镜像回退。

### 恢复演练

在独立环境恢复 PostgreSQL、业务 MinIO、必要 Redis 状态与加密密钥，重建或恢复 Milvus；核对租户权限、对象可读、报告引用、任务终态和成本统计。记录真实恢复耗时与数据缺口，再谈 RPO/RTO。

## 13. 事故回答模板

「用户看到什么 → 影响哪些租户/任务 → 是否停止新写/新任务 → 哪层证据定位 → 可逆止损 → 验证恢复 → 数据与成本对账 → 防止复发」。

例如用户看到重复文本：先区分 SSE 重复渲染、回调重复落库、两个 Worker 同时调用模型；分别看 eventId、runId、Pending 所有权与 Provider callId。只在前端去重可能掩盖后端重复计费，必须沿整条链确认。

## 14. OWASP 补充：把防御变成逐入口的验收条件

### 14.1 SSRF：校验的不应只是输入时的字符串

OWASP 区分仅访问固定目标与任意外部目标，并强调应用/网络两层控制；跟随重定向可能绕过初始校验。见 [SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。

对本项目可列验收：初始域名、解析到的 IPv4/IPv6、每次跳转地址、实际连接目标、端口/协议、响应大小与时间；并限制内网/元数据出站。当前 validate_external_url 明确不解析 DNS，因此本节是加强与验证清单，不是宣称这些全部完成。

### 14.2 HTML 清洗后再改写仍可能破坏安全边界

OWASP 提醒，清洗后继续修改 HTML，或交给会改变它的库，可能使清洗失效；清洗库本身也应维护。见 [XSS Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)。

应沿本项目 Markdown→公式→高亮→链接处理→v-html 的真实顺序检查最后写入 DOM 的值。测试覆盖报告、Agent 消息、资产预览和生成物，不只一处 Markdown 组件；普通 Vue 文本插值与主动 HTML 插入也要区分。

### 14.3 上传不是扩展名白名单一项检查

Content-Type 可由客户端伪造，文件签名也不能单独解决所有风险；要结合文件名、内容、权限、存储与资源限制。见 [File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

项目测试可分别覆盖：伪扩展名、超大展开、超长页数/时长、损坏文件、转换进程超时、临时磁盘耗尽、下载对象越权。测试资料应人工构造，结果要区分「拒绝」「受控失败」「可见警告」「完整处理」。

### 14.4 模型 Guardrail 不能接管授权

工具调用仍要校验用户权限、会话上下文和具体参数；额外审核模型只能是防御层之一。见 [LLM Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)。

在固定攻击预算下，测恶意内容是否改变目标、触发未授权工具、跨租户读取或泄露秘密。只看模型有没有说「我拒绝」不够，最终工具副作用与数据访问收据才是判定依据。

## 15. 指标补充：分位数不能直接平均

Histogram 保存测量分布的聚合信息，属性集会形成不同指标流；增加标签会扩大基数和存储/内存成本。参见 [OpenTelemetry Metrics 数据模型](https://opentelemetry.io/docs/specs/otel/metrics/data-model/)。

本项目的扩展设计可为请求、检索、模型调用、工具和排队分别建延迟分布，使用有限的 provider/tool/status 标签。runId、requestId 和原始 query 更适合受控日志/Trace，而不是每个值都成为时间序列标签。

不能把三个实例的 P95 取平均就称全局 P95；应合并兼容的分布或原始样本后计算。平均延迟可以按总耗时/总次数加权计算，也不能无权平均各实例的平均值。当前未部署完整指标采集链，本节是可审阅的观测设计。

## 16. 报告改进幅度时同时给分母和样本

例如「40/50 个问题满足任务标准」要说明问题覆盖范围、模型版本、语料、预算、标注方法及失败类型；小样本的两题差异不宜包装成稳定提升。质量/延迟/成本应一起报告，避免靠更大模型和更多工具调用获得改进却遗漏新增成本。

建议保留同一批问题的逐题前后结果，区分检索失败、生成失败、引用失败、格式失败与暂时 Provider 错误。将不确定结果交给复核，而不是为了表格好看强行计为通过。
