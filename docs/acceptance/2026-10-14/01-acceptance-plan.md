## 1. 执行入口与交付内容

1. 阅读本方案，准备账号、环境、固定样本与上线范围。
2. 打开“全功能验收记录.xlsx”，按批次筛选“功能用例”。每项填写状态、实际结果、证据位置、缺陷编号、测试人和时间。
3. 按 02-full-test-cases.md 查看全部详细用例。核心主流程按 E2EA-001 至 E2EA-022 连续执行，并保留对象 ID 账本。
4. 按 03-api-acceptance.md 完成没有 UI 入口的接口与内部能力。每行正常、鉴权、越权/不存在、参数四个子项分别写结果。
5. 用 04-feedback-report-template.md 汇总反馈，连同填好的表格、证据和脱敏日志交回。06-coverage-matrix.md 用于核对没有遗漏页面或接口。
6. 权限对照与接口四子项记录格式见 05-permissions-and-api-records.md。

## 2. 状态、优先级和执行规则

状态只用：未执行、执行中、通过、失败、阻塞、不适用。通过必须有实际结果与证据；被依赖挡住用阻塞，不用不适用。缺少短信、模型、OCR 等上线承诺的依赖也是阻塞。
不适用只用于明确不交付的部署分支，并由上线负责人说明范围、理由和对外说明；仍须验证禁用分支。不得用它隐藏失败、跳过核心流程或省略已宣称支持的格式。

P0：核心链路、真实性、权限隔离、凭据安全、持久化和上线必需能力。P1：重要功能和异常/边界。P2：非关键显示或文案问题；用例优先级与缺陷严重度分开记录。
缺陷严重度：S0 为数据泄露/破坏或重大安全故障，S1 为核心不可用/错误结论/上线必需功能缺失，S2 为重要功能异常但有可靠绕行，S3 为轻微显示或文案。

任何关键数字、来源、授权、终态和持久化检查失败都单独判失败，不能被平均分、成功率或其他通过项抵消。UI toast 不是数据库成功证据，HTTP 202 不是任务完成证据，401 不是健康 UP，hash/memory/mock 不证明生产质量或持久性。

## 3. 环境与账号

本地入口：http://localhost:5173。浏览器业务 API 前缀 /api，实际 Java 路由从 /auth、/workspaces 开始；AI 默认 http://localhost:8003。
完整上线验收还需要正式构建的隔离预发布地址，验证 HTTPS、反向代理、深链接、Cookie、SSE、探针、备份与重启。不能把本机 Vite 可访问直接视为上线完成。

建立可销毁 QA-A 和 QA-B，P1/P2 是 QA-A 共享项目，PP 是 A 创建的私有项目。

| 账号 | 归属与角色 | 用途 |
|---|---|---|
| A | QA-A OWNER；可另建第二工作区 | 项目创建、管理和主流程 |
| B | QA-A ADMIN，非 PP 创建者 | 管理协作、创建者配置优先级与私有项目隔离 |
| C | QA-A MEMBER | 普通权限、升级降级、邀请接受/拒绝 |
| D | 仅 QA-B OWNER | 跨工作区越权对照 |

用各自浏览器配置或无痕环境隔离 Cookie。真实短信没有接入前可使用已有合法测试账号推进非短信测试，但注册/短信登录/重置/换绑依然记阻塞；读取 Redis 验证码不能证明真实短信送达。

登记：操作系统、浏览器版本/尺寸、代码 commit 和工作树哈希、部署方式/实例数、数据库迁移版本、生产拟用 LLM/Embedding/搜索提供商与模型版本、文件工具版本、配置开关、资源规格、预计并发、P95 阈值/超时、成本上限、备份恢复目标。
只登记凭据是否配置和短指纹，不提交真实密码、API Key、Cookie、短信码或数据库敏感内容。

## 6. 标准答案与证据

使用 fixtures/README.md 与 questions.json。关键数值 26 万、6 周、3 人、12000 QPS、99.95% 均有固定原文；吞吐/SLA 为目标；旧版 32 万/8 周用于冲突；资料没有生产实测延迟。
质量不比较模型全文逐字一致，比较事实、单位、来源支撑、冲突、缺口、拒答边界和合法结构。每个拟上线模型组合标准题至少 3 次，记录每次失败而不只平均分。

证据命名建议：`用例ID_日期_步骤.png`、`用例ID_network.json`、`用例ID_log.txt`。保存 HTTP 状态和业务 code、操作前后对象 ID、变更前后值、run/trace/call ID、耗时/Token/模型信息。网络文件/HAR 必须移除 Cookie、Authorization、API key 等敏感字段。
每项记录“实际结果”而不是只填通过。失败必须给最短复现步骤和证据；阻塞必须给依赖项；不适用必须给范围决定与负责人。

## 7. 上线判定条件

1. 全部范围内用例和 API 子项有执行记录；核心 P0 全部通过，没有未执行、失败、阻塞或未审批不适用项。
2. 没有未关闭 S0/S1；S2 只能经负责人明确记录影响、绕行和修复计划后接受，影响核心/权限/数据真实性的 S2 不豁免。
3. 关键事实与引用全部可追溯；跨租户/项目/私人资料无泄露；真实短信/LLM/Embedding/拟交付搜索与文件格式可用。
4. 对固定发布候选重新执行正常、冲突、不足、失败恢复、多用户隔离与持久化核心闭环；自动测试与正式构建完成。
5. 预发布 TLS/Cookie/CORS/SSE、数据库迁移、备份恢复、生产密钥、探针告警、网络暴露、并发/资源/成本阈值、回滚方案有证据。
6. 上线负责人签署支持范围、已接受问题与发布/回滚责任。没有测试证据时结论为待验收；发现阻塞时为暂不可上线。

通过功能验收能提供具体版本可上线的证据，不能保证未来运行永不出现故障。最终结论会同时写明覆盖、配置、模型、部署、剩余风险与观察计划。

## 8. 收到反馈后的最终验证

我将先核对每个编号和证据、补齐未执行/阻塞/不适用的范围决定，再复现全部失败项，按确认的需求修复，并对修改的链路做回归。
随后执行前端 test/type-check/build、Java 单元/集成与迁移验证、Python pytest/契约与安全 Harness、真实基础设施检索/隔离、标准模型问题集、浏览器完整核心闭环和预发布部署检查。
前端当前可运行 `npm.cmd run test`、`npm.cmd run type-check`、`npm.cmd run build`；Java 为 `mvn.cmd test`/`mvn.cmd package`；AI 为 `.venv\Scripts\python.exe -m pytest`。这些命令以届时实际脚本和依赖为准，失败不能忽略。当前测试文件清单见覆盖矩阵；现有自动测试不等于全功能已有自动覆盖。
最终输出“可上线 / 限定范围可上线 / 暂不可上线”的证据报告，并列未解决事项、准确发布版本和复验结果。本轮没有进行发布、破坏性测试或修改业务数据。
