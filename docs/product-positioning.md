# Shinkou Insight 产品定位

## 一句话定位

Shinkou Insight 是面向企业和团队的 **证据驱动项目规划与决策审查工作台**：它主动搜集内部与外部资料，组织方案对比和可行性分析，起草标准计划书，并用可追溯的审查门禁控制结论进入发布和执行。

它不是一个泛聊天机器人，也不是只会生成文档的写作工具。它的交付物是：

```text
目标定义 → 证据搜集 → 方案/竞品对比 → 可行性判断 → 计划书 → 人工审查 → 行动落地
```

## 目标用户

| 用户 | 核心任务 |
| --- | --- |
| 企业创新 / 战略团队 | 判断一个方向是否值得投入，形成立项依据 |
| 产品与研发负责人 | 比较内部方案、市场同类方案和替代路径 |
| 项目经理 | 把调研结果拆成里程碑、负责人和验收标准 |
| 风控、法务、审计 | 追溯来源、识别冲突、确认关键断言 |
| 管理层 | 快速阅读结论、风险、资源需求和待决策事项 |

## 核心模块

### 1. 规划中枢

以项目为单位管理目标、问题、成功指标、约束、负责人和决策日期。规划准备度不能只看文案是否写完，还要检查资料、研究运行、报告和行动项是否到位。

### 2. 主动研究与工具编排

Agent 根据研究目标拆解任务，优先检索项目知识库；资料不足时调用经过授权的网络搜索或连接器。每次调用都记录工具、输入、时间、来源和结果，用户可以从结论回到原始证据。

### 3. 方案与市场对比

比较维度至少包括：目标用户与场景、功能与能力、成本与周期、资源依赖、风险与合规、可替代性。系统要区分：

- 事实：能回到来源的原文或数据；
- 推断：基于多个事实作出的判断；
- 建议：结合约束条件提出的行动方向。

### 4. 可行性分析

从业务价值、技术实现、资源与成本、时间窗口、合规和运营能力六个维度给出结论。每个维度都要展示依据、未知项、失败条件和需要谁确认，而不是只给一个总分。

### 5. 标准计划书

默认结构为：执行摘要、背景与问题、目标与范围、方案对比、可行性、风险与假设、里程碑、资源预算、审查记录、行动项和证据附件。支持 Markdown / PDF 导出，报告版本与生成运行、模型、Prompt 和引用绑定。

### 6. 审查中心

计划书发布前至少经过：目标范围、证据覆盖、市场对比、可行性、反证检查和人工签署。审查结果分为通过、待核验、阻断和升级，不允许用“模型看起来很确定”代替人工确认。

## 反虚构制度

默认开启以下规则：

1. 事实性结论必须绑定引用，引用包含来源、版本、位置和检索时间。
2. 金额、比例、日期、规模等数字没有来源时直接阻断发布。
3. 内部资料与外部网页发生冲突时，保留两方证据并升级给负责人，不自动挑选“更像真的”一方。
4. 外部来源必须标记来源类型、抓取时间和可信度，不得伪装成内部事实。
5. Agent 无法找到足够证据时必须输出“证据不足”和下一步搜集建议。
6. 计划书中的事实、推断和建议必须分段展示，不能把推断写成事实。
7. 关键结论需要人工签署；修改结论后自动要求重新审查。
8. 规则开关、审查结果、用户修改和最终发布版本进入审计日志。

## 关键状态机

```text
DRAFT
  → RESEARCHING
  → COMPARING
  → FEASIBILITY_REVIEW
  → HUMAN_REVIEW
  → APPROVED
  → IN_EXECUTION
```

任何阶段都可以回退到 `EVIDENCE_GAP` 或 `CONFLICT_REVIEW`。报告生成完成不代表项目通过审查；只有满足门禁并完成签署，才允许进入 `APPROVED`。

## 当前产品界面落点

- **项目概览**：展示项目数据状态，并直接引导进入规划链路。
- **规划中枢**：编辑规划输入、查看准备度、对比框架、标准计划书结构和审查前置条件。
- **Agent 对话 / 任务队列**：执行资料搜集、竞品研究和证据提取。
- **报告**：沉淀带引用的研究结论和计划书版本。
- **审查中心**：运行结构化检查、配置反虚构规则、处理阻断项和人工签署。
- **行动项 / 评估**：将结论转为责任人和回归用例，验证计划是否持续有效。

## 产品边界

Shinkou Insight 可以帮助团队更快地形成高质量决策材料，但不替代项目负责人、法务、财务或管理层的最终判断。系统必须把“建议”与“批准”分开，把“发现资料”与“证实结论”分开。

## 数据真实性约束

- 项目目标、资料、调研运行、报告、行动项、评估用例、规划草稿和审查记录均以服务端数据库为唯一事实来源。
- 页面请求失败时展示加载失败或空状态，不使用 localStorage、随机 ID、静态业务记录或本地时间冒充已保存、已运行或已审查。
- 审查策略和结构化审查运行分别持久化在 `project_review_policies` 与 `project_review_runs`，运行结果由服务端按项目真实数据计算并写入审计日志。
- UI 中的规则名称、计划书章节和对比维度属于产品制度定义，不代表已经存在的项目事实；只有数据库返回的记录才可进入事实统计和发布门禁。

## 后续建设优先级

1. 为每条事实建立 claim-evidence 关系和冲突来源视图。
2. 增加竞品来源白名单、网页快照和过期提醒。
3. 将计划书发布门禁接入报告版本状态机和工作区审计日志。
4. 增加“证据覆盖率、未决假设、冲突项、计划偏差”的管理层摘要。
