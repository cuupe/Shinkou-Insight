# 对话处理方式升级说明

## 1. 目标

Agent 对话不再把每个问题都当成完整调研，也不再默认追加一次回答检查。运行时会根据问题的范围、是否依赖项目资料以及用户选择，采用合适的处理路径：

| 页面选项 | 内部路径 | 适用场景 |
| --- | --- | --- |
| 自动选择 | `AUTO` | 默认选项。简单问题直接回答，资料型问题查证，多部分问题先拆分。 |
| 先整理步骤 | `PLAN_AND_SOLVE` | 比较、评估、排查、迁移等包含多个子任务的问题。 |
| 边查边确认 | `REACT` | 需要根据已获得资料决定是否继续查找的问题。 |
| 回答后检查 | `REFLECTION` | 对完整性、引用边界和不确定性要求较高的问题。 |

`DIRECT` 只作为运行时的内部结果，不在页面上单独展示。它用于自动判断简单问题无需额外检索时的最低成本路径。

## 2. 运行时流程

### 2.1 自动选择

选择器是确定性的轻量规则，不消耗模型调用：

1. 多部分、比较、评估或较长问题进入 `PLAN_AND_SOLVE`。
2. 既需要项目上下文又适合逐步查证的问题进入 `REACT`。
3. 需要解释、排查、决策或其他质量检查的问题进入 `REFLECTION`。
4. 其余问题直接生成回答。

这只是选择执行路径，不会把任何隐藏推理展示给用户。

### 2.2 边查边确认

每轮只允许选择一个动作：

```text
SEARCH_INTERNAL -> 项目资料观察 -> 再次判断
SEARCH_WEB      -> 网页资料观察 -> 再次判断
FINAL           -> 进入回答生成
```

每次运行最多 4 轮，重复查询会立即停止并进入回答阶段。联网搜索仍受 `allowWebSearch` 控制，项目检索仍受 `toolMaxCalls` 和单次 `topK` 限制。

模型只返回动作、查询和简短的操作摘要；系统不会要求或存储隐藏思维链。工具结果以独立证据事件进入回答上下文。

### 2.3 先整理步骤

计划模型最多生成 4 步，每步只能是：

- `SEARCH_INTERNAL`：核对项目资料；
- `SEARCH_WEB`：在已授权时核对外部资料；
- `SYNTHESIZE`：停止查找并组织回答。

计划生成失败时，运行时根据问题生成最小备用计划；计划过于保守而没有查项目资料时，项目型问题会补做一次受限检索。

### 2.4 回答后检查

检查模型只输出是否通过、问题、修正建议和置信度。检查发现可执行问题时最多触发一次修正；检查服务不可用时保留可用初稿，并在运行记录中标记检查不可用，不把整次聊天置为失败。

## 3. 前后端接口

聊天请求的 `config` 新增：

```json
{
  "strategy": "AUTO",
  "reflectionEnabled": true,
  "allowWebSearch": false,
  "topK": 3
}
```

`strategy` 可取 `AUTO`、`REACT`、`PLAN_AND_SOLVE`、`REFLECTION`。Java 后端负责白名单校验并透传，Python Runtime 负责选择和执行。

运行记录的完成事件增加内部字段 `strategy`，用于审计和回归测试。页面只展示有意义的阶段名称，例如“确定回答路径”“查找并核对资料”“整理处理步骤”“回答质量检查”，不直接展示实现术语或无意义的“已修改为某某范式”。

## 4. 事件与可观测性

三条路径共享现有 `node.*`、`tool.*`、`evidence.added`、`message.*` 和 `run.*` 事件：

| 用户可见阶段 | 事件节点 | 记录内容 |
| --- | --- | --- |
| 确定回答路径 | `CHAT` | 当前运行选择的内部路径，以及选择完成状态。 |
| 整理处理步骤 | `PLAN` | 步骤数量、步骤状态和每一步的执行结果。 |
| 查找并核对资料 | `SEARCH` | 当前轮次、动作、查询结果数量。 |
| 调用工具 | `tool` | 工具名称、查询、成功/失败和结果数量。 |
| 整理回答 | `SYNTHESIS` | 初稿生成和最终回答完成状态。 |
| 回答质量检查 | `REFLECTION` | 检查是否通过、是否修正以及失败降级原因。 |

事件中的 `strategy`、`action` 和 `step` 用于开发审计，页面通过已有 `meta` 保存，不将它们拼成面向用户的技术提示。

## 5. 失败与安全边界

- 所有项目检索经过现有工具注册表，遵守每次运行的最大调用次数。
- 网页搜索只有在请求授权且路径需要时才执行；没有结果时不会生成虚假来源。
- 计划和动作均经过 Pydantic 白名单校验，未知动作不会直接执行。
- 重复查询、超过轮次和工具错误都会转成可审计观察，最终仍由回答模型明确说明资料不足。
- 证据仍作为不可信来源数据注入，文档或网页中的指令不会升级为系统指令。
- 前端不展示模型隐藏思维，只展示阶段、工具、证据和回答结果摘要。

## 6. 验收场景

1. `1+1=?`：不检索、不追加检查，直接返回。
2. “这个项目使用什么数据库？”：自动进入资料查证路径，只取少量相关来源。
3. “比较 A、B、C 并给出迁移建议”：自动先生成步骤，再执行必要检索。
4. 手动选择“边查边确认”：可看到每轮查找、结果和下一步决定。
5. 手动选择“回答后检查”：可看到一次检查，必要时看到修正后的回答。
6. 结构化输出不可用或工具失败：保留可用回答，过程面板显示具体降级原因。

## 7. 引用标记位置

回答中的引用标记必须贴近被支持的事实句或段落，格式为 `[来源ID]`，不能在文章末尾把多个序号集中列出。前端优先使用模型输出的段内标记；对于历史消息或模型漏标的回答，会根据段落文本与来源标题、摘要、摘录的词项相关性，把未标记来源就近补到对应段落，同时保留底部折叠区用于查看完整来源详情。

## 8. 知识库切分与检索

上传阶段不再由 Java 先按固定字符数写入临时切片；资料完成索引后，页面与检索统一读取 AI 服务生成的 `parser-v2` / `chunker-v2` 记录。Markdown 标题和 DOCX Heading 会作为 `section_title` 保留，段落和列表优先在自然边界切分，长度限制只作为兜底。

中文自然语言问题不会直接作为一个完整全文检索词。检索器会提取实体词以及二元、三元词，并与原有 PostgreSQL 全文检索结果合并；Milvus 查询同时正确读取集合定义的 `chunk_id` 主键。没有配置外部 Embedding 时仍可使用本地哈希向量完成索引，但它只适合本地兜底，语义召回质量需要配置真实的 Embedding 服务。
